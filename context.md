### 2026-07-11 — Fix real bug: blank views because modules ran before data loaded (Session 4)

**User report:** "I DONT SEE ANYTHING. I TOLD YOU TO KEEP THE TWO SUB PROJECTS - STUDENT PERFORMANCE AND SALES ANALYSIS RIGHT ? I DIDNT SAY YOU TO REMOVE THOSE. FIRST TAKE A DEEP BREATH AND UNDERSTAND THE WHOLE CODEBASE YOU BUILT, READ context.md, then find where you went wrong and fix that issue first"

**Self-criticism:** In Session 3b I jumped to a conclusion ("data.js and charts.js were corrupted") and "fixed" the wrong thing. The modules were never the issue — they ARE registered (Node ESM test proved it). The real bug was in the boot order.

**Root cause (correctly diagnosed this time):**

Old `js/app.js` boot sequence:
```
1. initTheme()
2. buildNav()              ← creates <section id="view-X"> placeholders
3. initRouter()            ← calls show() → dispatches "viewchange"
4. await loadStudents()+loadSales()   ← takes ~200ms
5. activate(initial)       ← data is finally ready
```

Between steps 3 and 4, the router dispatched `viewchange`, which fired the listener that called `activate("overview")`. At that moment, `data` was still `null`. The module's `setup()` did `const { students, sales } = data;` → `TypeError: Cannot destructure property 'students' of 'data' as it is null`.

The error was caught (somewhat) and silently swallowed because the activate flow had already set `activeModule = mod` BEFORE calling setup. So:
- `activeModule` is set to the failed module
- The throw kills the setup, but doesn't reset activeModule
- Inner HTML remains empty
- 200ms later when data finally arrives, `activate("overview")` runs again
- The check `if (activeModule && activeModule.id === id && activeModule.refresh)` matches
- It calls `refresh()` instead of `setup()` — but refresh() doesn't recreate innerHTML
- **User sees empty view forever**

I had been blaming file corruption. The actual issue was an architectural race condition.

**Fix:**

1. **Reordered boot** in `js/app.js`: now `initTheme → buildNav → DATA LOAD → initRouter → activate`. Router only initializes after data is ready.
2. **Made `activate()` data-aware** — if `data` is null, it stores `pendingView` and returns. When data arrives, the pending view is activated.
3. **Wrapped module setup in try/catch** with visible error UI (no more silent failures — any future module bug shows in the page).
4. **Reset innerHTML before each setup** so failed/refreshed modules always start fresh.

- The browser-side `getComputedStyle` error during my Node test is expected (browser API only)
